# Council synthesis after three Delphi rounds (2026-09-22)

The two judges produced independent R0 proposals, cross-reviewed each other in R1–R3, and revised twice. Strict convergence was not reached at the three-round ceiling: final cross-scores are 4/7 for proposal 1 and 5/7 for proposal 2. No extra council round is authorized. This synthesis merges sound decisions and explicitly rejects the mechanisms invalidated by live evidence. It is a design candidate for premortem and user review, not an assertion that either proposal passed.

## Authority and constraints

- User intent: fix eight open b24api issues and all eight audit observations, including 19 executable examples. Preserve an object-oriented, extensible design and keep method-agnostic client responsibilities separate from endpoint registry and application storage. Backward compatibility is waived. Keep specs local; do not publish externally.
- Both judges received the user-supplied synthetic portal webhook and ran read-only probes. The credential must not appear in public documents. The old solo spec is a starting point, not a frozen design.
- Evidence classifications: LIVE means observed on the supplied portal during council, SOURCE means pinned code/PHP inspection, FIXTURE means deterministic offline test, UNVERIFIED means portal-dependent hypothesis. A LIVE observation from one portal is not a universal Bitrix guarantee.

## Reconciled architecture

Keep the existing `contracts/` + mechanics split. Each new public value object is frozen and has one responsibility. Avoid a parallel framework: extend `Request`/`WireRequest`, `RateCoordinator`, traversal drivers and reports through small composed contracts. The four companion specs remain transport/errors, traversal, registry, and examples. No implicit compatibility shims for 2.2.0. No method catalog inside b24api.

1. **Route**: exact-case logical `Request.method` plus per-request typed `RouteKind.BARE|JSON|API_V3`. Resolve the physical URL from the request route at dispatch time, including `/rest/api/<user>/<token>/` rebasing, so a bare-default client can send a V3 request. Validate base and suffix before I/O. Route survives `with_parameters`, direct fan-out, traversal and `call_bytes`; CLI call/list/verify-keyset expose it. Physical batch and inner commands are BARE only until a full alternate route contract is proven. Reject JSON/V3 commands before physical batch construction with correlated negative outcomes; no silent direct fallback. LIVE: `.json` works for direct JSON/form and batch envelope, but inner `cmd` with `.json` fails; V3 method inside classic batch can be mis-dispatched to another classic handler. Rejecting it is correctness, not convenience.
2. **Credential-safe logging**: protect the actual logger emitting HTTPX INFO request records in the pinned HTTPX version; attach a reference-counted filter before handlers format `msg` and `args`. The shield handles concurrent transports, injected HTTPX clients used through the transport, cleanup, and unrelated requests without replacing application handlers or levels. Scope the guarantee to b24api-owned requests and their known HTTPX INFO URL records; exceptions and b24api diagnostics use the existing redactor. Test raw records and formatted output for success/failure/timeout and both encodings; test logger cleanup and unrelated traffic. Do not claim a Python record factory protects fields added afterward or arbitrary custom formatter-created exception text.
3. **Typed failures**: V1 scalar and V3 object errors are distinct typed `ApiResponseError`s; malformed objects remain `ProtocolError`. V3 `validation[].field` is an opaque string (e.g. `filter.taskId`), with bounded, immutable, redacted detail. Carry original `B24ApiError`, `normalized_code`, `retryable`, and computed `ReplayDisposition` through `CommandFailure`, reference outcomes, blocking violations and `IncompleteTraversalError`. The caller classifies a throttle without an extra diagnostic call.
4. **Throttle**: `RateCoordinator.acquire` takes the set of logical methods in a physical request, checks host-wide header cooldown and per-method `operation_time_limit` deadlines before taking a permit. A batch command throttle inside HTTP 200 creates a method deadline; default fallback 120 seconds, configurable and budget/cancellation aware, with repeated signals extending rather than shortening. No automatic batch replay. The `time.operating` gauge is observational unless a method-specific sequence is shown monotone and its reset semantics qualified. LIVE: `crm.item.list` accumulates, `im.recent.list` can freeze, others can stay zero. Do not impose generic proactive pacing or call a frozen gauge healthy. Later optional meter policy may be enabled per qualified method.
5. **Positional ABI**: a `PositionalArguments`/slot layout value object owns exact arity and contiguous ordered top-level slots. Control injection is transactional, writes in existing top-level slots, can create a final leaf inside an existing nested container, preserves fixed predicates and top-level order, rejects near-match casing/overlap and checks actual encoded bytes. LIVE: `task.elapseditem.getlist` accepts four-slot unscoped and five-slot task-scoped forms, both HTTP 200 but different totals; scenario 13 uses five-slot form. The current form encoder drops empty objects, which can silently change arity; positional form/batch dispatch fail preflight until an exact preserving encoding is proven on bytes and portal. Direct JSON is the initial supported representation. Layouts for `task.commentitem.getlist`, `task.items.getlist` and `task.item.getlist` are separately qualified.
6. **Traversal composition**: separate request progression (`PageStride`/cursor) from completion proof (`ClosureRule`/witness), and use one `CompletionGate` as authority for operation state and assurance. The gate receives every admitted binding, scheduled page, delivered/acknowledged page, negative outcome, violation, stop reason and cleanup result. `COMPLETED` requires all admitted bindings accounted for, no failed/unknown/not-executed outcomes, no rejected page, emitted/admitted delivery equality, and qualified terminal witnesses. `COMPLETED_WITH_FAILURES` never sets operation-wide `exhausted=true`; `exhausted` requires all bindings naturally exhausting. Reports keep bounded aggregate evidence; per-page identity/offset reconciliation can be windowed, not unbounded sets retained in public reports. A validated caller stop is distinguished from source exhaustion and yields only bounded-prefix assurance.
7. **Server granularity**: offset contracts declare server page granularity separately from requested wire limit, decoded cap and page-index increment. For endpoints that floor `start` to 50-row boundaries, stride must be aligned and full-page width checked; `start=932` cannot be used as the next offset after 900. Sparse selected pages use a qualified raw bound and fixed server stride, not visible `next` or selected row count. One-based page controls advance 1 while rows per page may be 10. Misaligned or unqualified combinations fail before I/O or as a blocking violation. LIVE: `crm.requisitelink.list` and `tasks.task.list` floor offsets; 437/437 direct and physical batch rows on the supplied portal with 50 stride, so the old 582/400 mismatch is not a general decoder proof.
8. **Cursor domain**: `CursorSpec` declares whether cursor is an exclusive range predicate or opaque server token, and declares ignored values. LIVE for `im.dialog.messages.get`: `LAST_ID` is exclusive `id < c`; a missing numeric ID works as a bound; `LAST_ID=0` or null is ignored and restarts at head; negative/non-numeric values error. Thus empty after a valid positive LAST_ID is a qualified end of that range on this portal. Reject ignored values before dispatch and if produced by progression. Do not add an anchor probe for this method: the proposed `c+1` probe can create false negatives after deletion and wastes a request. Opaque cursor methods can require a separate positive-control contract, but only after their ambiguity is demonstrated.
9. **Keyset final call (#5)**: use existing lower-level `BOUNDARY_ID_SEEN` mechanics only when a method-specific upper bound is established for the same filter, an upper fence is enforced, and the exact boundary identity is admitted in the traversal. A separate probe row is not an admitted witness. If absent or unqualified, retain empty confirmation or report weaker/incomplete assurance. Inspect sequential, auto and fast independently. Do not use chat-specific LAST_ID probes as a generic keyset boundary.
10. **Caller stop reach**: expose a validated per-page stop policy across cursor, ordinary offset, keyset and reference traversals where the strategy can retire a binding before scheduling its next page. Counted physical batched tail rejects caller stop at construction; a direct-tail strategy may support it. The callback cannot edit rows, and an exception is a failure. Page-boundary events provide a durable acknowledgement seam: caller commits rows and checkpoint before requesting the next event. Resume replays an overlap into keyed storage and validates the expected overlap within a finite budget. The client owns truthful page/cursor evidence, the application owns persistence.
11. **Counted tail**: use structural checks over every scheduled offset/window, exact total, identity and duplicate page signature. Do not claim two sampled pages verify the whole tail. The 582/400 observation remains a targeted research gate; a current 437-row portal gave full direct and batch results. Compare first divergent raw offset before deciding whether there is an endpoint-specific batch incompatibility or a client stride error. Provide explicit direct-tail dispatch if supported mechanics need it; no hidden replay of already-emitted rows.
12. **Registry**: source `@restMethod` extraction covers `im.v2.*` and exact case, with `im.v2.Chat.Message.CommentInfo.list` as a required card. `FIRST_ID` on `im.dialog.messages.get` is marked unusable for traversal; `LAST_ID` contract and ignored cursor values are documented with evidence. The portal's `methods` enumeration is not an existence or coverage oracle: LIVE it omitted numerous callable methods. Issue #4 closes only after extraction coverage, not a manual one-card patch.
13. **Examples**: all 19 remain required, with frozen independent oracles, public client operation, method-specific assumptions, outcome/report meaning, bounded resources and opt-in live fixture where portal behavior matters. Four source-level gaps (#1, #11, #12, #19) require an actual client capability before the example is supported. Scenario 13 must use five-slot task-scoped request; scenario 14 must treat 582/400 as unconfirmed on this portal; scenario 4 pins the live-accepted chat selector (do not assume DIALOG_ID if this method accepts CHAT_ID). Keep high-water metrics as observed maxima: bounded assertions ordinarily, exact peaks only with deterministic barriers.

## Rejected / deferred alternatives and why

- Reject proposal 2's `VERIFY_ANCHOR` for chat `LAST_ID`: live exclusive-range semantics disprove its premise and the probe can report false incomplete after row deletion. Retain only for a separately qualified opaque-token endpoint.
- Reject proposal 1's completion ladder as written: final review found missing not-executed, binding-count and delivery-count guards. Keep its single-gate architecture, repair the full invariant above.
- Reject proposal 1's positional path as written: it did not guard empty-slot loss in form/batch, a silent wrong-scope response. Use proposal 2's exact writer and encoding gates plus the newly observed dual-arity contract.
- Reject generic proactive throttle from `time.operating`: the gauge is method-dependent and can freeze; keep it as evidence until qualified.
- Reject a process-wide record factory as a complete logging guarantee: it runs before `extra` and exception formatting. Use a scoped filter at the verified emitting logger and test its actual limits.
- Reject physical batch JSON/V3 inner routes despite `.json` envelope support; live probes show inner route incompatibility and V3 misdispatch.
- Defer direct-tail root-cause claims pending first-divergence probe on the original >400-row fixture.
- Do not preserve 2.2.0 API forms for their own sake; retain only proven semantics. Explicit migration notes can help users but do not constrain the architecture.

## Evidence gates before implementation claims

Pin source/client SHA for every fixture. Reconfirm method-specific route, PHP slot arity, raw total, ordering, form/batch encoding and cursor domain on a disposable portal before promising it as universal. A successful HTTP response is insufficient where wrong scope or silent row loss is possible. Keep the user-provided webhook in a private task input, never in published spec text or tests.

## Premortem changes to the implementation plan

The separate two-judge premortem found five recurring ways an assurance feature could silently fail. Incorporate these controls before the spec is considered implementation-ready:

1. **Gate wiring must be observable.** Only `CompletionGate` constructs a strong terminal report. Each traversal family registers its supported event classes and supplies a positive-control fixture for negative outcomes, not-executed bindings, page rejection, delivery acknowledgement and cleanup failure. An unregistered or partly wired family cannot express `COMPLETED`. Add an architecture test prohibiting terminal report construction elsewhere. Offset structural checks do not prove a stable snapshot under concurrent mutation; snapshot assurance stays weak without method-specific stability evidence.
2. **Route is required, not defaulted.** `Request.route` has no implicit `BARE`; factories may offer `Request.bare(...)` for ergonomics, but reconstruction must carry the explicit route and provenance through every path. A matrix test covers direct, call_bytes, fan-out, batch, traversal and CLI. Physical dispatch compares the route in the originating logical request with the wire request, so V3 cannot silently revert to classic bare. This is permitted by the user's waiver of backward compatibility.
3. **Qualification is reusable.** Extend the existing read-only capability-verification pattern with versioned, local method profiles containing portal provenance, source SHA and evidence class. Profiles may be loaded by examples and applications without adding a hard-coded method catalog to b24api. Known silent-corruption modes fail closed; merely unknown completeness may run only under an explicit weak-assurance request and cannot produce the strong label. A semantic scope oracle, not just HTTP 200 and byte identity, qualifies positional layouts.
4. **Shield has a positive control.** Tests require that the expected HTTPX INFO record was emitted and the filter actually rewrote it, covering logger-name drift. Pin a tested HTTPX upper bound and run an upgrade probe. Register/release under one lock with in-flight request accounting so closing one transport cannot remove protection from another. Check full formatted exceptions at the transport boundary as well as `msg`/`args`.
5. **Examples prove ergonomics and efficiency.** Recipes import only public b24api exports (enforced by an import-boundary test), record setup/declaration size, oracle and evidence class, and measure direct/batch request counts. A capability gap remains an explicit expected-failure/blocked case until public support lands; a skipped live fixture never becomes a passing live claim. For retryable batch failures, expose a bounded public retry/resume plan derived from per-command outcomes if examples show callers otherwise rebuilding client classification logic; do not automatically replay unsafe commands. Qualified method profiles can keep declarations out of every recipe while the core remains method-agnostic.
