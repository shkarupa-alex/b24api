# Registry и версионированные профили методов

> Нормативная часть утверждённого дизайна. Реализация registry относится к `apidocs`; код ядра b24api не содержит каталога методов. Охват: #2, #4 и #6/1–2.

## Источник и provenance

Профиль конкретного REST метода хранит exact-case имя, route, selector/response shape, control contract, PHP source SHA и класс доказательства `SOURCE`, `LIVE`, `FIXTURE`, `UNVERIFIED`. Read-only qualification расширяет существующий pattern проверки capability; профиль можно загружать примерам/приложению без копирования деклараций в каждом рецепте. Известное silent corruption (wrong scope, ignored cursor, floor offset) fail closed. Неизвестная полнота допускает лишь явно запрошенную слабую assurance, никогда сильный `COMPLETED`. LIVE относится к конкретному порталу/версии, не обещает универсальный Bitrix контракт. Для positional схем semantic oracle проверяет scope, а не только HTTP 200 и wire bytes.

## `im.dialog.messages.get` (#2)

Первичная карточка и машинный metadata запрещают `FIRST_ID` как traversal cursor: старое утверждение об ASC от начала ошибочно, серверное окно способно пропустить середину при успешном завершении. Frozen oracle `{3573,3575,12561,29991,30211}` демонстрирует silent loss. Квалифицированный `LAST_ID` DESC на предоставленном портале — exclusive range `id < c`, положительный несуществующий bound допустим; 0/null сервер игнорирует и возвращает head, negative/non-numeric дают typed error. Поэтому 0/null отвергаются до dispatch или как progression, а пустой ответ после валидного положительного bound означает конец диапазона ниже него. Не делать `c+1` probe: он не нужен для range и может дать ложный incomplete после удаления. Проверить 1/3/50 page size и различать source evidence от synthetic fixture.

## `im.v2.*` (#4)

Registry generator извлекает PHP `@restMethod` annotations controller actions вместе с classic source, сохраняет exact case и выдаёт coverage diff; вручную добавленная одна карточка не закрывает #4. LIVE portal `methods` enumeration пропускает callable методы и не служит coverage oracle. Обязательная карточка `im.v2.Chat.Message.CommentInfo.list`: read-only, вход — 1–100 `messageIds` одного исходного chat; 101+ даёт `TOO_MANY_MESSAGES`, mixed chats — `MESSAGES_IN_DIFFERENT_CHAT_ERROR`, если ни один ID не существует, LIVE получен `MESSAGE_NOT_FOUND`; если часть ID существует, LIVE возможен HTTP 200 с частичным `commentInfo` без отсутствующих ID. Пустой список LIVE даёт V1 `error="100"` с внутренним PHP class в description, который нельзя показывать без redaction. Отсутствие ID в ответе неоднозначно: несуществующее сообщение или существующее без комментариев; нужна сверка с независимым oracle существования. Результат имеет `commentInfo` и `usersShort`, не плоскую коллекцию; pagination нет, input chunking остаётся явным. Метод резолвит пост в `dialogId`/счётчик комментариев, сами комментарии читает `im.dialog.messages.get`. `messageCount` служит независимым oracle для read-only обхода комментариев. Указать права и отличие от `im.recent.list`, который не перечисляет comment chats без участия webhook пользователя. Проверить source extraction, exact spelling, 100/101, mixed/missing/empty с разными ожидаемыми кодами и opt-in live читаемый comment chat. Не подменять чтение `im.chat.parent.join` с побочным эффектом.

## Прочие обязательные профили

`task.elapseditem.getlist`: две LIVE формы — четыре unscoped слота и пять task-scoped; профили раздельны, scenario 13 использует пять. Envelope `next=50` в ответе не является допустимым top-level `start`: такой `start` повторяет первую страницу; использовать только `NAV_PARAMS.iNumPage` и обязательную duplicate identity проверку. Fixture `total=53` помечен FIXTURE, а не LIVE. `task.commentitem.getlist`, `task.items.getlist`, `task.item.getlist` получают самостоятельные PHP/live qualification. `tasks.task.list` и `crm.requisitelink.list`: LIVE server offset granularity 50. `im.search.user`: raw total и стабильность order пока gate, не утверждённый универсальный факт. `crm.timeline.comment.list`: `>ID` игнорируется. `crm.item.list`: `start=-1` подавляет total/next, `>updatedTime` действует LIVE. `im.recent.list`: `total=-1`, `time.operating` может застывать. Exact-case V3 route и object-valued errors также хранятся как профиль метода. Для каждого такого факта сохранить portal/source SHA и fixture, а не переносить его по аналогии на соседние методы.

Для набора запрошенных ID нужен публичный `RequestedIdentitySet`/аналог: вход фиксируется до вызова, полученные `messageId` сверяются с ним, пропущенные помечаются `missing_unresolved`, а не доказанным отсутствием. 100-ID success fixture строится из одного чата; mixed 100 может вернуть mixed-chat error раньше проверки лимита.

## Воспроизводимый extraction gate

База `apidocs` на момент спеки `f916127b08c7786e7171b915474ce8308636d02a`; существующий `scripts/scan_php_controllers.py` уже содержит `RE_REST_METHOD` и поиск controller files, поэтому расширять его, а не создавать второй scanner. Входной manifest фиксирует `bitrix_root`, SHA исходного PHP snapshot, список module/controller roots и SHA самого scanner. Каждая извлечённая запись хранит exact `@restMethod`, путь PHP файла, class/action и source span. Если два разных action дают одинаковое exact имя, generator выдаёт collision report и не повышает registry snapshot; если имена различаются только регистром, обе записи сохраняются, lowercased runtime dump не перезаписывает exact spelling. Coverage gate сравнивает множество извлечённых annotations с машинно читаемым registry по exact имени, выводит missing/extra с provenance и падает при missing; portal `methods` используется лишь как дополнительный наблюдательный сигнал. Fixture включает несколько контроллеров, inherited/trait actions и case collision.
