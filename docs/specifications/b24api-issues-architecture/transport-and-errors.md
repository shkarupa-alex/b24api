# Транспорт, маршруты, ошибки и ограничения

> Нормативная часть утверждённого дизайна. База `154ddbafb5821b7975fa5bb9e59d8c79797d109f`; совместимость 2.2.0 не требуется. Охват: #1, #7, #8; аудит 1–3, 5.

## Маршрут

`Request.method` сохраняет точный регистр логического REST имени. Обязательное `Request.route: RouteKind` принимает `BARE`, `JSON`, `API_V3`; фабрики могут дать удобный явный выбор. Транспорт строит URL в момент dispatch из request route: `/rest/<user>/<token>/<method>`, `/rest/<user>/<token>/<method>.json`, `/rest/api/<user>/<token>/<method>`. Проверить структуру base и запретить двойной суффикс до I/O. `with_parameters`, `WireRequest`, `call_bytes`, direct fan-out, обходы и CLI `call/list/verify-keyset` сохраняют route и provenance; dispatch сравнивает исходный request и wire route. Смешение bare и V3 в одном клиенте разрешено. Тестовый портал показал case-sensitive V3 и `im.v2.*`; canonicalization имени недопустима.

Физический `batch` и внутренние команды поддерживают только `BARE`, пока не доказан другой контракт. `JSON`-envelope сам по себе работает, но `.json` в `cmd` на тестовом портале не работает; V3 имя в классическом batch способно тихо попасть в другой handler. Любая иная route во внутренней команде отклоняется до отправки пачки с коррелированным отрицательным outcome. Скрытый direct fallback запрещён; явный `DirectDispatch` разрешён. Проверки: матрица JSON/form × все routes, binary, facade, CLI, batch rejection; live успех метода отдельно от mock правильного URL.

## Защита журналов

Для b24api-owned запросов credential не должен появиться в сыром `LogRecord`, `getMessage()`, handler output, исключении или отчёте при HTTPX INFO. На поддерживаемом диапазоне HTTPX найти фактический emitting logger. На нём устанавливается фильтр до handler formatting, редактирующий известные URL поля, `msg` и `args` для зарегистрированных запросов. Регистрация, refcount, учёт in-flight и release защищены одним lock; закрытие одного транспорта не снимает фильтр с другого. `httpx.AsyncClient`, переданный через transport, учитывается. Чужие запросы, logging level и handlers не меняются. Остаточный риск документируется: прямое использование caller-owned `AsyncClient` после закрытия транспорта и отдельный `httpcore` DEBUG logger вне этой гарантии; для включённого DEBUG требуются отдельный тест и явная политика приложения. Исключения и собственные diagnostics проходят существующий redactor; фильтр не объявляется защитой произвольного custom formatter. Тест с синтетическим sentinel доказывает, что INFO record действительно испущен и фильтр сработал на success, 4xx, timeout, JSON/form; проверяет concurrent transport, logger drift, закрытие и полный формат exception. Upgrade HTTPX требует повторить положительный контроль.

## Типизированные ошибки

`ProtocolCodec` принимает V1 scalar `error` и V3 object `{code,message,validation}`. Корректный V3 при HTTP 200/4xx даёт `ApiResponseError`; malformed форма, пустой code и неверные типы дают `ProtocolError`. `validation[].field` остаётся непрозрачной строкой: LIVE встречается `filter`, dotted `filter.taskId` допустим по контракту. V3 code (`BITRIX_REST_V3_EXCEPTION_VALIDATION_REQUESTVALIDATIONEXCEPTION`, `BITRIX_REST_V3_EXCEPTION_METHODNOTFOUNDEXCEPTION`) сохраняется exact в `normalized_code`; locale-dependent `message` не участвует в классификации. Эти два кода не retryable. Неизвестный V3 code тоже не retryable без явной policy qualification. Детали immutable, redacted до `to_safe_dict()` и ограничены: не более 4 уровней, 32 validation items, 256 Unicode code points в каждом поле и сообщении, 8 KiB суммарной безопасной сериализации; усечение явно отмечается `truncated=true`. `CommandFailure`, reference outcome, blocking violation и `IncompleteTraversalError` сохраняют исходный `B24ApiError`, `normalized_code`, `retryable` и вычисленный `ReplayDisposition`. Классификация `OPERATION_TIME_LIMIT` доступна без диагностического запроса. Автоматического replay опасной физической пачки нет.

## Ограничитель

`RateCoordinator.acquire(work_class: WorkClass, *, methods: frozenset[str], budget: DeadlineBudget | None = None)` проверяет host-wide `Retry-After` и per-method deadlines до permit. `OPERATION_TIME_LIMIT` внутри HTTP 200 batch создаёт deadline для соответствующего метода; защитный fallback 120 секунд настраиваем, повторы продлевают дедлайн, не сокращают его. Budget, cancellation и close прерывают ожидание с типизированной причиной. Другие методы хоста продолжают работать. `time.operating` пока только наблюдение: LIVE на синтетическом портале `crm.item.list` накапливает его, `im.recent.list` может замереть, другие дают нуль. Proactive pacing допустим только для отдельно квалифицированного метода с известной монотонностью и reset semantics. Проверить fake clock, все методы физической пачки, budget, повторный throttle и отсутствие unsafe replay.

## Метрики и приёмка

High-water означает измеренный максимум, а не настроенный capacity. Обычный тест проверяет `0 <= peak <= bound`; точный пик проверяется лишь барьером. Для #1, #7, #8 необходимы публичные и transport-level тесты с независимым sentinel; live портал служит opt-in подтверждением endpoint semantics. Изменения API документировать migration notes без совместимых shim ради старых форм.

## Исполнимый контракт coordinator и batch admission

Не терять существующий `WorkClass` fairness cycle. Публичная форма: `await RateCoordinator.acquire(work_class: WorkClass, *, methods: frozenset[str], budget: DeadlineBudget | None = None) -> Permit`. Один coordinator принадлежит клиенту и его portal host, используется всеми direct, batch и traversal вызовами этого клиента; transport даёт нормализованный host при construction, incompatible injected host preflight reject. Состояние под одним async condition: host-wide header deadline, `dict[method, monotonic_deadline]` и прежние очереди по `WorkClass`. Истёкшие записи удаляются при каждом acquire/observe; размер карты ограничен 1024 активными методами, переполнение даёт явный `RatePolicyCapacityError`, не молчаливое игнорирование throttle.

Физический batch с хотя бы одним cooling методом ждёт целиком до максимального срока всех своих методов; coordinator не делит команду/пачку и не делает replay. Независимая физическая пачка без cooling методов продолжает работу и сохраняет fairness `WorkClass`. Header `Retry-After` блокирует весь host. `observe_api_throttle(method, code, delay?)` принимает direct ошибку и per-command batch `OPERATION_TIME_LIMIT`, обновляет `deadline=max(old, now+delay)`; уже выданные permits не отменяет, их ответы независимо классифицируются. Budget/cancellation удаляет waiter без потери permit, close будит его с типизированной причиной. Все повторные вызовы того же клиента используют тот же coordinator; новый клиент не разделяет состояние без явного shared coordinator. Тест с fake clock: 9-command mixed batch блокируется целиком при одном cooling методе, другой метод в отдельном direct запросе проходит, повторный signal продлевает срок, истечение budget возвращает typed cause, unsafe команда не replay.

## Positional wire representation и preflight

`PositionalArguments(slots: tuple[Slot, ...], layout_id: str)` хранит каждую позицию как `Present(value)` либо `EmptyObject`, `EmptyArray`, `Null`; `Omitted` допустим только для неиспользуемого trailing suffix, никогда между занятыми слотами. Layout задаёт точную arity, тип и ownership каждого слота, case-sensitive control path и semantic scope. `write_control(path, value)` возвращает новый объект атомарно: при ошибке исходный неизменен. Top-level порядок, все placeholders и nested paths сравниваются с фактическим serialized JSON body до dispatch. Form/batch encoding отвергается preflight, пока encoder и live semantic oracle не докажут сохранение пустых слотов. Для пятислотового elapsed запроса layout: `(taskId, order, filter, select, params)`, для четырёхслотового: `(order, filter, select, params)`; `NAV_PARAMS.iNumPage` меняется внутри существующего `params`, `start` и envelope `next` не используются как control. Rejection cases: неверный регистр `NAV_PARAMS`, попытка добавить шестой top-level slot, заменить fixed `taskId` либо использовать пропущенный внутренний slot.

## LIVE ограничения V3 на синтетическом портале

V3 route принимает JSON; form body с валидными полями на тестовом портале даёт `...INVALIDJSONEXCEPTION`, поэтому `API_V3` + form/multipart reject preflight. Для `tasks.task.list` V3 LIVE `limit`, `offset`, `start`, `page`, `pageSize` не продвигают страницу; `result` содержит `items` без `total/next`. Общая V3 offset/cursor/counted traversal capability поэтому отсутствует: профиль метода должен доказать конкретный control и closure до допуска. На данном портале keyset с явным `order id asc` и фильтром-тройкой `[ ["id", ">", bound] ]` продвигается; это LIVE профиля, не универсальный V3 синтаксис. Пример V3 #19 проверяет route и типизированную ошибку без обещания V3 pagination.
