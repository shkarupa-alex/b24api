# Исполняемые examples: 19 сложных сценариев

> Нормативная часть утверждённого дизайна. Источник требований — [issue #6](https://github.com/shkarupa-alex/b24api/issues/6) и его [аудит](https://github.com/shkarupa-alex/b24api/issues/6#issuecomment-5772905794). Пакет `examples/` создаётся при реализации, а не при написании спеки.

## Роль примеров

`examples/` — небольшой набор исполняемых рецептов, который доказывает, что публичный b24api выражает bulk extraction, bounded traversal, прерывание и частичную синхронизацию без повторной реализации клиентского ядра в коде приложения. Каждый рецепт содержит короткий README/docstring: входной fixture и права, точные REST method/регистр параметров, selector/shape, выбранную операцию и dispatch, policy идентичности/дублей, смысл `OperationReport`, границу гарантий. Пример запускается offline с deterministic fake через публичный injected `Transport`/`WireTransport`, без webhook в CI. Отдельный `--live`/эквивалентный явный запуск требует disposable portal и нужную fixture; её отсутствие = skip с причиной, не «успех с нулём строк». Passing LIVE evidence содержит capture с portal fingerprint, timestamp и digest каждого физического ответа, подписанный независимым recorder-ом; verifier использует закреплённый публичный trust anchor без caller override. Переименование offline summary или подпись выдуманного capture собственным ключом не является LIVE evidence.

Чтения read-only по умолчанию и `ReplaySafety.SAFE` только для доказанных чтений. Создание тестовых записей opt-in, cleanup/reconciliation явны, их запросы не помечаются безопасными к replay без основания. Не выводить webhook и credential-bearing download URLs. Один публичный `b24api.testing.ScriptedTransport` с frozen table должен обеспечить deterministic offline requests; неизвестный запрос — fixture failure, не пустой success. Shared helpers допустимы лишь для transport fixture, setup и маленького SQLite sink/checkpoint на стандартном `sqlite3`, без `pumpe`/`sqlmodel`. Важные методные предположения и критерии остановки видны в самом рецепте. Каждый пункт имеет независимое ожидаемое множество ID/счётчик, определённое **до** вызова клиента; положительный HTTP ответ сам по себе не является oracle.

У всех multi-parent рецептов bounded число команд/буферов, correlation с parent, отдельные completion/failure/unknown, explicit duplicate policy. Durable checkpoint записывается после commit результата; при возобновлении overlap перечитывается в keyed sink. `EARLY_CLOSED`, caller stop, failure и exhaustion отображаются отдельно. Performance claim включает фактическое число физических и логических запросов до/после, без обязательного абсолютного времени. Исходные четыре gap (#1, #11, #12, #19) считаются закрытыми только после passing публичного API example **и** минимального клиентского исправления; тест до исправления может быть ожидаемым failure/skip, но не ломать CI.

## Размещение и команды проверки

Рекомендуется `examples/README.md` с таблицей 1–19, тематические файлы `examples/<scenario>.py`, общие `examples/_support/` только для deterministic transport/sink, `tests/examples/` с frozen fixtures и expected IDs. Каждый файл запускается как документированная команда без implicit network; live флаг отделён. CI запускает offline suite на 3.12+ и проверяет, что отсутствуют реальные URL/секреты. В summary теста выводятся scenario number, client SHA, method-card SHA, `OperationReport` state/assurance, expected/observed count, requests и live/fixture provenance. Для каждого № есть строка в `examples/README.md` со статусом `supported`, `endpoint-limited` либо `blocked by client gap`; статус меняется только после указанных тестов.

## Условия закрытия #6

Все 19 номеров имеют runnable example, deterministic offline check и требуемые opt-in live результаты там, где portal semantics существенны. Для #1, #11, #12, #19 есть именно публичное client capability, а не комментарий о workaround. Если portal fixture опровергнет исходную гипотезу, в issue записываются SHA и сравнение oracle до изменения статуса. Endpoint limitation допускает ослабленный, но правдивый отчёт. Подзадача или PR без работающего рецепта не закрывает umbrella issue.

## Обязательная проверка удобства публичного API

Каждый рецепт импортирует только публичные экспорты b24api; статический тест запрещает импорт из внутренних модулей. Зафиксировать размер setup/declaration, независимый oracle, класс evidence, число direct/batch запросов и bounded peak памяти/активных bindings. Условия метода разрешено брать из версионированного локального профиля, чтобы не переписывать схему во всех 19 файлах; ядро остаётся методно независимым. Если обработка retryable batch outcome заставляет рецепт заново классифицировать ошибки и собирать команды вручную, добавить минимальный публичный bounded retry/resume plan из per-command outcomes без автоматического unsafe replay. До исправления такой рецепт считается blocked, а не supported. Skip live fixture не превращается в passing LIVE claim.

Для сценария 13 семантический oracle проверяет, что вернулись elapsed items **нужного task**, а не только HTTP 200/total/byte shape. Для сценария 14 582/400 не объявляется текущим дефектом на всех порталах: с `entityTypeId=2` direct и batch дали 437/437; без фильтра позднее total=812. Это разные выборки и моменты. Для сценария 4 селектор `CHAT_ID` подтверждён live и не заменяется на `DIALOG_ID` по аналогии с другим методом. Для сценария 1 `LAST_ID` есть exclusive `id < bound`; 0/null запрещены, а пустая страница после допустимого bound — корректная граница диапазона.

Issue #9 про `pumpe`/`sqlmodel` открыт после фиксации пользовательского объёма #1–#8; он отдельный dependency issue и не блокирует эти SQLite примеры. `docs/recipes.md` после реализации ссылается на новые рецепты и не дублирует устаревающие правила.

Механический предел `examples/_support`: не импортировать `b24api.traversal`, `b24api.references`, `b24api.batch` и другие внутренние пути; не более 10 публичных helper declarations вне fixture data и sink. При превышении — вынести повторяемую механику в публичный клиентский контракт, а не расширять support.
